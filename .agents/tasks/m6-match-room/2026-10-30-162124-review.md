# Match room with chat, player reporting, disputes, help flag and organizer queue (M6)

This change adds the M6 match room. Players report scores, and the opponent confirms them or reports different ones. Matching reports complete the match through `refreshStage`. Conflicting reports make it disputed, and only an organizer can resolve it. Each room has a chat that is live over SSE, players can raise a help flag, and an organizer queue sits at the top of the admin Matches tab. Result writing moves from `stages.ts` into a new `services/matches.ts`, which the admin tab, the room and the future M7 API share. "Disputed" and "reported" are derived from `match_reports` rows and never stored as a status. I checked the code against each user decision and the binding plan decisions. I also re-ran check (0 errors, 0 warnings), lint, the unit tests (24 files, 289 tests) and the full e2e suite (9 passed). Nothing is staged and HEAD is still 98d079b.

Watch for: only minor gaps. Live chat messages can be dropped by a page reload that is in flight (confirmed mechanism, narrow window). `live.ts` never reconnects after an HTTP error response, which matters behind the M9 proxy (likely). A player who causes a dispute sees it twice, once styled as success (confirmed). A few phase and permission paths have no tests.

**Verdict**: APPROVED

## High-level view

The reporting rules are a pure module, `matchReports.ts`, shared by the server and the UI. A report is `saved` while the opponent hasn't reported, which covers both a first report and an edit. It is `agreed` or `disputed` when it answers the opponent's report, and `closed` once both sides have reported. `services/matches.ts` applies the rules under the stage row lock and re-reads the match after locking. All phase rules live in the service: tournament running, stage running, match `ready`, reporter an entrant, and no draws in elimination stages.

Stale reports are handled twice. `refreshStage` deletes a match's reports and clears its help flag when the entrants change or the match leaves ready/completed. Reads also ignore any report whose stored entrants differ from the current ones. An organizer or API key override replaces every report with one `organizer`/`api_key` row, so the room can tell who decided.

Authorization sits at the edge. The room's `report`/`help`/`message` actions require a user. `override`/`clear`/`clearHelp` go through `requireTournamentAdmin`. "Organizer" means an org member with a trusted session, matching `requireOrgRole`. All input goes through Zod, and chat bodies render as text.

Live updates use an in-process pub/sub keyed by tournament, published after each commit. The client reloads data on every `open` and every `update` and appends chat messages directly. Two weak spots: an in-flight reload can overwrite an appended message, and `live.ts` gives up for good after a non-200 response. The admin queue isn't live, which follows the user's decision.

There are tests for every rule the user listed and a two-browser e2e for the whole room flow. Help phase rejections, draws reported by players and the room SSE endpoint's per-match filtering have no tests.

<summary>Issues (6)</summary>

1. **Appended chat lost on concurrent reload** (minor). The room's `messages` is `$derived(data.messages)`, so any `invalidateAll()` that is in flight when a `chat` event arrives replaces the appended message with older server data. Merge locally received messages by id with `data.messages` instead of overwriting.
2. **EventSource never recovers from HTTP errors** (minor). `live.ts` only reports `error`. A non-200 response, such as a proxy 502 during a restart, closes the EventSource for good while the badge keeps reading "Reconnecting…". When `readyState` is `CLOSED`, recreate the source after a delay.
3. **Dispute shown twice and styled as success** (minor). The `report` action returns `room_disputed` as `form.message`, which renders in the green `alert success` above the card's warning alert with the same text. Return no message for `disputed` (or map it to a warning).
4. **Live badge reads "Reconnecting…" before the first connect** (minor). `connected` starts `false` on both pages, so the first paint says "Reconnecting…". Use a neutral initial state or a separate "connecting" label.
5. **"Your matches" rows lack stage and group context** (minor). In multi-stage or multi-group tournaments the list can show two `#1` rows that look the same. Add `matchContext(match)` to the rows in that section.
6. **Missing tests for help phase, player draws and room SSE filtering** (minor). Add db tests for `requestHelp` on a waiting match and on a non-running tournament, and for a player-agreed draw in round robin. Add a check that the room endpoint drops other matches' chat.

### Stale reports across upstream corrections

```
refreshStage(row differs)
  stale = entrantsChanged || status ∉ {ready, completed}
  stale → DELETE match_reports WHERE match_id = row.id ; helpRequested = false
read side: sideReports() / getMatch() drop rows whose entrants ≠ current entrants
```

Agreed reports deliberately survive completion: the entrants are unchanged and the status is `completed`. That is what lets the room say "Both players reported this result."

### SSE delivery and the reload-on-open resync

JSON-encoding the payloads keeps chat bodies on one `data:` line, so a message body can't inject SSE fields. The room page keeps chat in a writable derived:

```ts
let messages = $derived(data.messages);
// chat handler
messages = [...messages, { ...message, createdAt: new Date(message.createdAt) }];
```

Every `open` and every `update` calls `invalidateAll()`. When a reload is in flight and its `listMessages` query ran before a new message was inserted, the `chat` event appends the message and the reload's result then overwrites it. The message comes back on the next reload. The window is narrow (confirmed mechanism), but it contradicts the "nothing is missed" claim in the M6 notes.

`live.ts` relies on EventSource's built-in retry. That covers network errors only. Under the spec, a response that isn't 200 with `text/event-stream` fails the connection for good. After a proxy 502/503 during an app restart (M9 runs behind Apache), the page stays static and the badge keeps reading "Reconnecting…" (likely). Both pages also start with `connected = false`, so the first paint shows "Reconnecting…" before the first connect.

### Room UI states

The `report` action maps `disputed` to `m.room_disputed()` as `form.message`. The page shows that in `alert success` with `role="status"`, and the result card then shows the same sentence again in `alert warning`. The plan already names one race, and it fails safe: a Confirm sent with scores the reporter has just edited becomes a dispute for an organizer to resolve. "Your matches" on the public list reuses the plain `#N` row. In a group-plus-playoff tournament a player can have a `#1` in each stage, and nothing tells the rows apart.

### Test coverage

The queue db test is reversed relative to the plan, so ordering by match number alone can't pass it. Not tested: `requestHelp` on a waiting match or a non-running tournament; a draw reported by both players in round robin/Swiss (`resultFor` is only covered through `setMatchResult` in Swiss); the room SSE endpoint dropping other matches' chat; and an untrusted member not counting as an organizer.

### Bundled change outside the plan

The change to `src/routes/+layout.svelte` replaces `resolve(localizeHref(...) as Path)` with a `ResolvedPathname` cast, because the new routes pushed the `Path` union past TypeScript's limit. No base path is configured, so the output doesn't change.
