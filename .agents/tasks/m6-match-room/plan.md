## Design decisions

1. **Disputed is derived from the reports, not stored.** `matches.status` stays exactly what the engine says (`refreshStage` overwrites it on every refresh). A ready match's progress (`ready`, `reported` = one side reported, `disputed` = the two sides disagree) comes from its `match_reports` rows through the pure `matchProgress()`. That gives one source of truth. Deleting stale reports clears a dispute automatically, and `refreshStage` needs no new status.
2. **`match_reports` stores the entrants it was made for**, like `MatchResult` does. Columns: `source` (`participant` | `organizer` | `api_key`), nullable `participantId` / `userId` / `apiKeyId`, `entrants`, `scores`. Player reports are unique on (matchId, participantId), so the reporter's edit is an upsert. When an organizer or (in M7) an API key sets a result, all reports are deleted and replaced by one `organizer`/`api_key` row, so the room can say who decided.
3. **Stale reports**: `refreshStage` deletes a match's reports and clears `helpRequested` whenever that match's entrants change or it stops being `ready`/`completed`. This is the engine's stale-result rule applied to reports. Reads also ignore reports whose `entrants` differ from the match's, as a second guard.
4. **Reporting rules live in a pure module** (`src/lib/matchReports.ts`, shared with the UI) and are applied by `services/matches.ts`. The rules: either player reports first, and the reporter can edit until the opponent responds. Equal scores complete the match through the existing result path (`refreshStage`). Different scores make it disputed. After that, players can't report again, and only an organizer can decide.
5. **Result writing moves from `stages.ts` to `services/matches.ts`**: `setMatchResult` (organizer/API key override, which now takes `by`), `clearMatchResult` and `loadMatch`. `stages.ts` keeps everything stage-level, and exports `lockStage`. `refreshStage` returns the ids of the matches it changed, so services can publish precise live updates. The admin Matches tab calls the matches service.
6. **Live updates use one in-process channel per tournament** (`src/lib/server/events.ts`). Events are `{ type: 'chat', matchId, message }` and `{ type: 'matches', matchIds }`, published after the transaction commits. Two SSE endpoints filter on the server: `matches/events` (the list forwards every `matches` event as `update`) and `matches/[id]/events` (the room forwards its chat as `chat` and `matches` events that include its id as `update`). On `update` the page calls `invalidateAll()`. Chat messages are appended directly. Every `open` (the first one and every reconnect) also calls `invalidateAll()`, so nothing is lost between SSR and connecting. There is a plain `ReadableStream`, a ping comment every 25 s, `retry: 3000`, and cleanup on `cancel()` and on `request.signal` abort. No new dependencies.
7. **Chat**: anyone who can view the tournament can read it (`loadTournament` visibility). The match's two entrants can post, and so can organizers, meaning an org member with a trusted session (decided at the edge). `asOrganizer` is stored at post time: true for organizers who aren't one of the match's players. Messages are 1–1000 characters and rendered as text.
8. **Help flag**: `matches.helpRequested`. Either entrant can set it while the tournament is running and the match is ready. Organizers clear it explicitly. Setting or clearing a result (agreement, override, clear) clears it, and so do stale entrants.
9. **Organizer queue extends the admin Matches tab**: a "Match queue" section at the top, followed by the unchanged per-stage list with result entry. Order: disputed, then help requested, then reported (waiting for the second report), then ready with no report. Ties go by stage, group, match number. Queue rows use `data-testid="queue-<id>"` and no headings. That keeps `e2e/helpers.ts` `playReadyMatches` (`li[data-testid^="match-"]`) and the `getByRole('heading', { name: 'Final stage' })` assertions working.
10. **Match pages use `matchNumbers` per group.** Byes have no number and no page (404). Lists show match number, entrants, score and status. There are no round labels, because raw template rounds don't match the bracket's renumbered columns.
11. **Shared `ScoreForm.svelte`** (two score inputs labelled `Score of {name}`, hidden inputs passed as children, `use:enhance`) replaces the admin list's inline form and is reused by the queue and the room. The markup stays identical: `form.result`, `input[name=score1|score2]`, the label spans.
12. **Zod at the edge**: `matchIdSchema` (`z.uuid`) for route params and the hidden `matchId`, `scoresSchema` for score fields, `messageSchema` for chat. Services still check the score numbers (for M7). Invalid ids give 404 or 400 instead of a Postgres 500.

## Open risks

- Reconnecting re-runs the load with `invalidateAll()`. With many open rooms in one tournament, each relevant update costs one load per affected room, which is fine at this project's scale.
- A Confirm clicked just as the opponent edits sends the scores the confirmer saw. If those no longer match, the match becomes disputed, which is safe, and an organizer resolves it. The live `update` makes this window small.
- SSE needs an unbuffered proxy (Apache `flushpackets=on`, long timeout) and a single process. That's noted for M9. LISTEN/NOTIFY would be needed for more processes.
- There's no chat rate limiting (only the 1000-character cap).
- `match_messages.authorId` is required. If M7 lets API keys post messages, it needs a migration.
- Times render with the server locale/timezone in SSR, and the client may differ (as `startsAt` already does).
