## Decisions

### 1. Profiles (`/u/[username]`)

**What M1 meant by activity.** `messages/en.json` defines it: `profile_show_activity` = "Show tournaments I'm registered for on my public profile", next to `profile_show_results` = "Show my results on my public profile". The M1 page rendered only a results placeholder and never any activity. So:

- **Results** (`showResults`) = the tournament history: every tournament the user plays or played that has started (`running` or `completed`), newest first, with organization, date, status, final rank (`#n`, or `–` while running) and their match record (won–drawn–lost), linking to the tournament and to its matches page.
- **Activity** (`showActivity`) = the tournaments the user is registered for that haven't started (`registration`, `check_in`), soonest first, **plus the organizations they belong to, with their role**. Organization membership isn't public anywhere else (the org page lists no members), so it needs a gate; reusing `showActivity` avoids a schema change, and its settings label becomes "Show the tournaments I'm registered for and my organizations on my public profile". This matches the brief's fallback list (memberships), while keeping M1's definition for the tournaments.
- **Date** = `startsAt`, or the tournament's `createdAt` when no start time is set, so every history row has one (the lists already sort by `coalesce(starts_at, created_at)`).
- **Linked accounts** stay ungated, as in M1 (dev identities filtered out). Drafts are never listed, for anyone.

| Section                                       | Gate           | Visitors and other users                                                           | Owner                                                                                      |
| --------------------------------------------- | -------------- | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| Header: avatar, name, @username, member since | none           | shown                                                                              | shown, plus "Edit profile"                                                                 |
| Results: history table                        | `showResults`  | shown when on; else the card says "This user keeps their results private."         | always shown; when off, a note "Hidden from others." with a link "Change this in settings" |
| Activity: registered-for list + organizations | `showActivity` | shown when on; else "This user keeps their tournaments and organizations private." | same as above                                                                              |
| Accounts                                      | none           | shown                                                                              | shown                                                                                      |

Hidden sections are filtered **in the service**: their data never reaches the page data (tested). User data stays out of the REST API (no API change for profiles).

**Service** `src/lib/server/services/profiles.ts`: `getProfile(username, viewerId: string | null)` returns `undefined` for an unknown user, else `{ user: { username, displayName, bio, avatarUrl, createdAt }, isOwn, visibility: { results: showResults, activity: showActivity }, accounts: { module, username }[], results: HistoryItem[] | null, activity: { tournaments: …[], organizations: { slug, name, role }[] } | null }`. It reuses `listUserTournaments` (extended with `participantId`, `createdAt`, `game`) and `listUserOrganizations`, and counts records with one query over `matches` with `status = 'completed'` whose `participant1_id` or `participant2_id` is one of the user's participant ids: `result.winner === null` → drawn, `result.entrants[result.winner] === participantId` → won, else lost. Byes (`bye`), unplayed (`waiting`/`ready`) and `skipped` matches don't count. The page load is thin and passes this through. A pure exported `matchRecord(participantId, results)` keeps the counting readable.

### 2. Steam game picker: the cache

- **Client**: `GET https://api.steampowered.com/IStoreService/GetAppList/v1/?key=…&include_games=true&include_dlc=false&include_software=false&include_videos=false&include_hardware=false&max_results=50000[&last_appid=N]`. Pages are in app id order; follow `response.have_more_results` with `last_appid` from the previous page. Stop after 20 pages or when `last_appid` doesn't advance. Each request has `AbortSignal.timeout(15_000)`. The body is checked with Zod (`response.apps[]` of `{ appid, name }`, optional `have_more_results`, `last_appid`); a non-OK status, invalid body or timeout throws. Skip empty names. Never log the URL (it has the key).
- **Tables**: `steam_apps (app_id integer pk, name text)` holds the list; `steam_app_list (id text pk = 'games', fetched_at, attempted_at, app_count)` records when it was fetched. The app list is replaced in one transaction (delete all, insert in batches of 5000 with `onConflictDoNothing`, upsert the `steam_app_list` row with `fetched_at = now`, `app_count`) only after every page arrived, so readers keep the old rows until commit and a failed refresh changes nothing but `attempted_at`.
- **Staleness**: the cache is fresh for 24 h after `fetched_at`. Every `search`/`find` first runs `ensureFresh()`: fresh → nothing; stale with rows → start a refresh in the background and answer from the old rows now (a typeahead must not wait ~10 s once a day); never fetched (`fetched_at` null) → wait for the refresh, so the very first search has results.
- **Concurrent refreshes**: in one process, callers share one in-flight promise. Across processes, a refresh first claims the `steam_app_list` row with `INSERT … ON CONFLICT (id) DO UPDATE SET attempted_at = $now WHERE attempted_at IS NULL OR attempted_at < $now - 10 min RETURNING id` (Drizzle `onConflictDoUpdate({ target, set, setWhere })`); no row back means another refresh started less than 10 minutes ago, so it doesn't fetch. The same window is the back-off after a failure: Steam being down doesn't make every search wait for a timeout.
- **Failure**: caught and logged (`console.error` with the message only); the old cache keeps serving.
- **Search**: `lower(name) LIKE '%q%'` with `\`, `%`, `_` escaped, ranked exact (0), prefix (1), word start `'% q%'` (2), anywhere (3), then `length(name)`, `name`, `app_id`; limit 10; empty query → `[]`. No index: a sequential scan over ~150k short names is tens of ms (pg_trgm is a later option, see Risks).
- **Shape**: `createSteamApps({ apiKey, fetch?, now?, timeout? })` returns `{ enabled, search(query), find(appId), refresh() }`; `steamApps = createSteamApps({ apiKey: STEAM_API_KEY })` is the instance's cache. The default `fetch` calls `globalThis.fetch` lazily. Tests make their own instances with `mockFetch` and `now`, so no test can reach Steam. Without a key, `enabled` is false, `search` returns `[]` and `find` `undefined`, and nothing is fetched.
- **Header image**: `steamHeaderImage(appId)` = `https://shared.akamai.steamstatic.com/store_item_assets/steam/apps/${appId}/header.jpg` (the URL Steam's own pages use). The tournament stores `{ appId, name, headerImage }`, copied when picked, so a stored game displays without a key or cache.
- **Env**: optional `STEAM_API_KEY` in `src/env.ts` (`schema: optional`), documented in `.env.example`, `compose.yaml` (`STEAM_API_KEY: ${STEAM_API_KEY:-}`) and the README.

### 7. i18n

- **Rule**: every user-visible string goes through Paraglide. That includes `ServiceError`/`IdentityError`/`AuthModuleError` messages, Zod messages in services and shared schemas, guard `error(…)` messages shown by `+error.svelte`, form action errors and flash messages. API-only code stays English (as decided in M7): `src/lib/server/api/**`, `auth/apiKey.ts`, `routes/api/**`. Startup errors for operators (`modules/config.ts`, `themes.ts`) stay English. Auth module names (`Discord`, `TETR.IO`, and `Development login`, which never exists in production) stay as the modules define them.
- **How**: `m.key(params)` is called when the error is created, so it follows the request's locale: `throw new ServiceError(m.registration_error_closed())`. Zod messages become lazy: `.min(1, { error: () => m.validation_name_required() })`, `z.uuid({ error: () => m.match_error_not_found() })`, `.refine(fn, { error: () => … })` (verified with the project's Zod: lazy errors work and don't affect `z.toJSONSchema`). Module-level message constants (`SLUG_TAKEN`, tetrio's `rankOptions`) move into the functions. The English text is copied verbatim, so existing tests that assert messages keep passing. Key names: `validation_*` for shared form rules, `<area>_error_*` for service rules (e.g. `match_error_not_found`, `registration_error_full`), `error_*` for page errors, `auth_error_*` for sign-in, `tetrio_*` for the TETR.IO module.
- **Module config labels** are built per call: `AuthModule.configFields` becomes a method `configFields?(): ConfigField[]` ("built per request, so labels follow the locale"); tetrio's `tetrioConfigFields` becomes a function.
- **Framework messages**: `handleError` in `hooks.server.ts` answers unexpected errors and unmatched routes with `{ message: status === 404 ? m.error_not_found() : m.error_title() }`, so `+error.svelte` never shows SvelteKit's English "Not Found"/"Internal Error".
- **Formatting**: `format.ts` gains `formatDateTime` (`toLocaleString` with `dateStyle: 'medium', timeStyle: 'short'`), `formatNumber` (`toLocaleString(getLocale())`) and `formatRecord` (`{won}–{drawn}–{lost}`, like `formatScore`). The tournament layout uses `formatDateTime` (fixes the crash), the profile's "member since" uses `formatDate(…, { year: 'numeric', month: 'long' })`, tetrio's `bracketFields` uses `formatNumber` instead of `toLocaleString('en')`.
- **`<html lang>`** already follows the locale (`app.html` `%paraglide.lang%`, replaced in `hooks.server.ts`); an e2e assertion pins it.
- **Second locale = a messages file + a settings entry**: today the strategy is `cookie, globalVariable, baseLocale` and there is no language switcher, so a new locale would be unreachable. Set `strategy: ['cookie', 'preferredLanguage', 'baseLocale']` in `paraglideVitePlugin` (`vite.config.ts`) and `--strategy cookie preferredLanguage baseLocale` in the `check` and `prepare` scripts (`package.json`), so browsers get their `Accept-Language` locale when it exists. With only `en` nothing changes. API clients don't send the cookie or browser languages, so service messages reach them in the base locale (English).
- **Guard**: `src/lib/messages.spec.ts` (pure, reads files with `node:fs`): (a) every key of `messages/en.json` except `$schema` is referenced as `m.<key>` somewhere under `src/` (excluding `src/lib/paraglide`); (b) no `.svelte` file has hardcoded text: strip `<script>`, `<style>`, comments, `{…}` (brace-matched) and tags, then fail on any remaining run of two or more letters; also fail on literal `aria-label`, `title`, `placeholder` or `alt` attribute values that contain letters. TypeScript already catches `m.<missing>()`. A tiny allowlist is fine if a real case needs it.

## Risks

- **Steam API drift.** The docs say service methods should be called with `input_json`; plain query parameters work for `IStoreService/GetAppList` today.
